Project Bharat-40B Blueprint

Architecture, Data, and Evaluation Protocol for a 40B India-First Frontier Model

1. Defensible Training-Token Budget

A target of 1.5T tokens provides a base-case assumption of 37.5 training tokens per parameter. However, a strict token budget cannot be set by parameter count alone. Our final budget is derived dynamically:

  • Proxy Ablations: We run proxy experiments at 2B and 7B scale, testing 1T, 1.5T, and 2T+ equivalent token budgets to map the efficiency curve against our target compute budget.
  • Unique vs. Consumed Tokens: We strictly distinguish between unique tokens in the dataset and tokens actually consumed. While general web data receives a single pass, high-quality subsets (mathematics, dense Indic corpora) utilize up to 4 repeated passes to extract maximum marginal value without crossing into wasted compute.

2. The "India-First" Capability Strategy

An India-first model requires epistemic grounding, not just linguistic translation. We design the corpus to reflect multiple, appropriately licensed regional viewpoints rather than encoding a single perspective as objective truth.

  • Core Domains: Deep ingestion of Indian history, geography, law (BNS, Constitution), public services (Aadhaar, UPI), education (NCERT, NPTEL), agriculture, healthcare, and localized economic/social contexts.
  • Language Tiers:
    • Primary Focus: Hindi, Bengali, Telugu, Marathi, Tamil, and Urdu (ensuring deep syntactic mastery).
    • Evaluation & Expansion: Gujarati, Kannada, Malayalam, Punjabi, Odia, and Assamese—scaled based on the availability of high-quality, non-machine-translated data.

3. Precision Extraction & Deduplication

Standard web-scraping destroys Indic morphology, code indentation, and logical structure.

  • Extraction: We utilize structured main-content parsing, deploying headless browser rendering specifically for JavaScript-dependent pages. We enforce careful Unicode normalization (NFC) to preserve Indic text and formatting, deliberately stripping boilerplate, cookie banners, and spam.
  • Staged Deduplication: We reject naive global deduplication, which often deletes superior recent text. Instead, we use: 1) Exact hashing, 2) Normalized hashes, 3) Near-duplicate MinHash matching, and 4) Quality-aware selection across snapshots to retain the best representative copy, rather than defaulting to the oldest.

4. Post-Training & Alignment Pipeline

We replace generic synthetic generation with a strict, multi-stage supervised and reinforcement learning pipeline:

  • Supervised Fine-Tuning (SFT): Focused on instruction-following, multilingual conversations, tool-use traces, and multi-step agent trajectories.
  • Preference Optimization (DPO): Chosen/rejected response pairs rigorously ranked on correctness, groundedness in Indian context, instruction compliance, and tool-use quality.
  • Reinforcement Learning (RLVR / GRPO): Driven by verifiable rewards. We use executable code tests (pass@k), mathematical verifiers, structured JSON tool-call checks, and multi-step task success.
  • Safeguards: Implementation of strict length penalties (to prevent reward hacking), invalid trace filtering, and aggressive decontamination of synthetic solutions.

5. Empirical Tokenizer Design

Token fertility numbers (e.g., 1.10 for code) are not universal properties; they are dependent on the tokenizer array and corpus. We do not assume a "sweet spot".

  • Candidate Training: We train candidate tokenizers across vocabulary sizes of 64k, 96k, 128k, and 160k.
  • Evaluation Metrics: Candidates are benchmarked against representative held-out corpora measuring:
    • Tokens per word (for Indic and English natural language).
    • Tokens per byte/character (for Code and Mathematics).
    • Resulting bytes or semantic content represented per token.
  • Cost/Benefit Analysis: The final vocabulary size is selected by balancing compression ratio and downstream proxy task performance against the parameter cost of the embedding and output layers, as well as byte-fallback behavior for unknown characters.

6. Evaluation & Selection Integrity

A held-out set that continuously influences data selection becomes silently overfit. We enforce strict boundary definitions:

  • Three-Tier Segregation: 1) Training data and permitted benchmark familiarization splits. 2) A distinct Development/Proxy set used strictly for tuning recipes and thresholds. 3) An immutable final test set used only once for final model evaluation.
  • Contamination Defense: Implementation of exact, fuzzy (n-gram), and semantic embedding contamination checks, alongside rigorous temporal (date-cutoff) and source-based splits to guarantee evaluation integrity.
